# DIRS Mathematical Formulation

Date: `2026-07-20`

Purpose: describe DIRS as a general method for learning reusable human skills,
not only paper-writing skills.

## General View

DIRS treats a human skill as a structured policy for turning an input situation
into a high-quality artifact or action trace.

```text
input:
  x = evidence, task state, chip, question, codebase, table, trace, or problem

output:
  y = artifact or behavior, such as an answer, search plan, research gap,
      paper section, code patch, experiment plan, review, or workflow

metadata:
  m = domain, task type, role, audience, venue, constraints, or evaluation mode
```

For a skill family `tau`, the training set is:

```text
D_tau = {(x_i, y_i, m_i)} for i = 1..N
```

DIRS assumes that expert behavior is generated by a latent directed structure:

```text
z_i = (S_i, pi_i, b_i, h_i)
```

where:

```text
S_i = selected connected skill sub-DAG
pi_i = topological execution or writing order
b_i = budget allocation over nodes
h_i = evidence bindings from nodes to x_i
```

The goal is to learn a reusable graph:

```text
G_tau = (V, E, Theta, H)
```

where:

```text
V = reusable skill nodes
E = directed dependency edges
Theta = learned priors, compatibility rules, budgets, and style/action policies
H = verifier or reward functions
```

## Skill Nodes

Each node is a small reusable unit of human skill.

```text
v in V
v = (family_v, c_v, a_v, gamma_v, rho_v, eta_v)
```

where:

```text
family_v:
  node type, such as context, gap, source lookup, mechanism, evidence,
  comparison, interpretation, scope, repair, or verification

c_v(x, m) in [0, 1]:
  content/evidence fit. This says whether the input contains the facts,
  claims, sources, or state needed to use the node.

a_v(y, pi, m) in [0, 1]:
  action/style fit. This says whether the node is executed or expressed in the
  right way for the task role.

gamma_v:
  evidence binding rule, mapping the node to required fields or source spans.

rho_v:
  support prior learned from training examples.

eta_v(x, m) in {0, 1}:
  rejection predicate. If eta_v = 1, the node is forbidden for this input.
```

For paper writing, a node might be:

```text
state one concrete benchmark gap
```

For search, a node might be:

```text
turn the user question into source-seeking queries
```

For research ideation, a node might be:

```text
contrast a crowded direction with an under-tested mechanism
```

## Skill Edges

Each edge says that one skill unit should come before another.

```text
e = (u -> v)
e = (u, v, d_e, t_e, rho_e, eta_e)
```

where:

```text
d_e(x, m) in [0, 1]:
  content dependency. This says whether v depends on u being established first.

t_e(y, pi, m) in [0, 1]:
  transition or execution fit. This says whether the movement from u to v is
  coherent for the target artifact or behavior.

rho_e:
  support prior learned from training examples.

eta_e(x, m) in {0, 1}:
  rejection predicate for misleading transitions.
```

The no-jump constraint is:

```text
for every selected edge (u -> v), pi(u) < pi(v)
```

For writing:

```text
metric/protocol -> result -> interpretation
```

For search:

```text
question decomposition -> source retrieval -> source comparison -> answer
```

For proposing a research gap:

```text
known field pattern -> unresolved limitation -> feasible testable gap
```

## Inverse Skill Learning

During training, DIRS infers the hidden skill trace that could have produced an
expert artifact.

```text
z_i* = argmax_z [
  A(z, y_i)
  + B(z, x_i)
  + C(z, m_i)
  - Omega(z)
]
```

where:

```text
A(z, y_i):
  artifact fit. The latent graph explains the expert output.

B(z, x_i):
  evidence binding. Selected content nodes are supported by the input.

C(z, m_i):
  role and domain compatibility.

Omega(z):
  complexity penalty for too many nodes, disconnected paths, or memorized
  paper-specific structure.
```

This step answers:

```text
Which reusable skill nodes did the expert use?
In what order?
Which evidence justified each node?
Which style/action behavior made the output effective?
```

## Support Estimation

For a domain with `N` training artifacts, node and edge support are estimated as:

```text
count_v = sum_i 1[v in S_i]
count_e = sum_i 1[e in S_i]
```

With simple smoothing:

```text
rho_v = (alpha + count_v) / (alpha + beta + N)
rho_e = (alpha + count_e) / (alpha + beta + N)
```

Support is a prior, not a command. A high-support node can be rejected if the
input lacks evidence. A low-support node can be selected if the target task
requires it and the evidence is strong.

## Training Objective

DIRS learns the graph that best explains training artifacts while remaining
reusable on held-out cases:

```text
G* = argmax_G [
  sum_i max_{z_i subset G} R_train(x_i, y_i, z_i, G)
  + lambda_val * R_val(G)
  + lambda_stab * Stable(G)
  - lambda_size * Complexity(G)
]
```

where:

```text
R_train:
  reconstruction, evidence binding, ordering, and style/action fit

R_val:
  held-out or replay performance

Stable:
  low graph drift across repeated training loops

Complexity:
  penalty for memorizing too many paper-specific nodes or edges
```

This is why multiple loops matter: each loop updates the latent graph, but the
system should stop when the graph stops changing meaningfully.

## Convergence Criterion

Let `G_t` be the shared graph after training pass `t`. A strict but practical
graph-stability check is:

```text
Delta_G(t) = GED(G_t, G_{t-1})
```

where `GED` is graph edit distance over:

```text
added nodes
removed nodes
split or merged nodes
added edges
removed edges
reversed edges
changed evidence bindings
changed compatibility or rejection rules
```

Let `P_t(x)` be the MCTS-selected sub-DAG for validation input `x` under graph
`G_t`, and let `R_val(G_t)` be the validation verifier reward. DIRS is converged
when, for `K` consecutive full-domain passes:

```text
Delta_G(t) <= epsilon_G
Jaccard(TopNodes(G_t), TopNodes(G_{t-1})) >= tau_node
Jaccard(TopEdges(G_t), TopEdges(G_{t-1})) >= tau_edge
P_t(x_j) == P_{t-1}(x_j) or equivalent for most validation cases
|R_val(G_t) - R_val(G_{t-1})| <= epsilon_R
Replay(G_t) passes
```

Recommended defaults:

```text
K = 3-5 full-domain passes
epsilon_G = 0 for structural edits, or near-zero for harmless label cleanup
tau_node = 0.95
tau_edge = 0.95
epsilon_R = 0.005 to 0.01 verifier-score change
```

Convergence should be behavioral, not merely textual. The graph is stable when
it selects the same useful sub-DAGs, preserves the same dependencies, passes the
same replay checks, and no longer improves validation quality.

## Training As Simulation

Training has two graph levels. First, DIRS infers a local skill trace for each
expert example:

```text
z_i^expert = (S_i^expert, pi_i^expert, b_i^expert, h_i^expert)
```

Then it merges those local traces into the current shared graph:

```text
G_t = Merge({S_i^expert}_{i=1}^N)
```

where merge canonicalizes repeated skills:

```text
shared node:
  same reusable content/action role across examples

shared edge:
  same dependency relation across examples

typed variant:
  similar role but different compatibility condition

rejection rule:
  pattern that repeatedly fails under simulation
```

Thus each local expert trace is a subgraph of the larger learned graph:

```text
S_i^expert subset G_t
```

The full graph is an extended skill space, not a single script to execute. It
contains alternatives, optional nodes, and domain variants. Therefore DIRS never
runs every node in `G_t` for one example. It selects a connected sub-DAG from
the full graph.

Given a graph snapshot, DIRS selects a candidate sub-DAG for each training case.
In the basic version, that snapshot is the current graph `G_t`. In the full
dual-loop version, Loop 1 first proposes a candidate graph `G'_t`, and Loop 2
evaluates that fixed snapshot:

```text
G_eval,t =
  G_t  in the basic simulation ablation
  G'_t in the proposer-critic training loop

S_i,t^sim = MCTS_Select(G_eval,t, x_i, m_i, H_train)
```

It then executes or decodes that sub-DAG:

```text
y_hat_i,t = Simulate(x_i, S_i,t^sim, pi_i,t, b_i,t, h_i,t)
```

and scores the result:

```text
r_i,t = H(y_hat_i,t, y_i, x_i, S_i,t^sim)
```

where:

```text
H:
  verifier that checks evidence support, edge order, role fit, budget fit,
  output quality, and similarity to the expert target only after generation
```

The graph update is performed by the outer learning loop, not by MCTS:

```text
G_{t+1} = UpdateOrReject(G_t, G'_t, {r_i,t}, {S_i,t^sim}, {y_hat_i,t}, replay_t)
```

## Proposer-Critic Graph Repair

DIRS can implement graph repair with two LLM roles plus a controller.

The training system has two non-overlapping loops:

```text
Loop 1:
  graph learning/editing

Loop 2:
  MCTS simulation over a fixed graph snapshot
```

```text
Proposer P:
  uses the current graph, input evidence, prior feedback, and training target
  to predict or revise inverse DAG structure and suggest repairs

Critic C:
  compares outputs, verifier reports, and compact DAG summaries; it does not
  need the entire shared graph unless it is judging an update to that graph

Controller A:
  accepts only edits that improve verifier or replay behavior
```

First, an initial inverse DAG can be inferred from each training example:

```text
S_i^expert = InverseDAG(x_i, y_i)
G_0 = Merge({S_i^expert}_{i=1}^N)
```

Then, at training round `t`, Loop 1 proposes a graph edit:

```text
G'_t = P(G_t, x_i, y_i, f_i,t-1)
```

Loop 2 runs MCTS simulation on a fixed graph snapshot. It does not mutate the
shared graph:

```text
S_i,t^sim = MCTS_Select(G'_t, x_i, m_i, H_train)
y_hat_i,t = Simulate(x_i, S_i,t^sim)
report_i,t = Verify(y_hat_i,t, x_i, S_i,t^sim)
```

The eval agent compares final results and returns feedback:

```text
f_i,t = Eval(y_hat_i,t, y_i, x_i, report_i,t)
```

For output-level feedback, the critic/eval agent can compare only the two final
results and reports. It does not need the full graph. If the feedback is being
used for graph repair, it can additionally receive compact sub-DAG summaries or
a graph diff:

```text
C_i,t = C(report_i,t, y_hat_i,t, y_i, summary(S_i^expert), summary(S_i,t^sim), diff(G_t, G'_t))
```

The critic/eval agent has three possible input levels:

```text
output level:
  C(report_i,t, y_hat_i,t, y_i)

selected-DAG level:
  C(report_i,t, y_hat_i,t, y_i, summary(S_i^expert), summary(S_i,t^sim))

full-graph acceptance level:
  C(report_i,t, y_hat_i,t, y_i, summary(S_i^expert), summary(S_i,t^sim),
    diff(G_t, G'_t))
```

Thus the critic does not always need the full DAG. It needs the full graph diff
only when deciding whether a proposed repair should modify the persistent shared
graph. For ordinary output feedback, the generated output, target output, and
verifier reports can be enough.

When graph repair is being evaluated, `C_i,t` includes:

```text
missing nodes
unsupported nodes
missing edges
wrong edge directions
over-specific nodes
changed evidence bindings
changed style/action rules
replay risk
```

The controller accepts the edit only if:

```text
Accept(G'_t) = 1
```

where:

```text
H_train(G'_t) > H_train(G_t)
or G'_t fixes a hard verifier failure
and Replay(G'_t) >= Replay(G_t)
and Complexity(G'_t) is bounded
```

Then:

```text
G_{t+1} =
  G'_t if Accept(G'_t) = 1
  G_t otherwise
```

This keeps the learning loop from becoming self-confirming. The same model may
not be the only source of generation, critique, and acceptance in a serious
evaluation.

The graph state is persistent across loops:

```text
G_0 -> G_1 -> G_2 -> ... -> G*
```

DIRS does not restart from zero for each round. Each example selects a local
sub-DAG from the current graph, but the final learned skill is the large shared
graph:

```text
S_i,t subset G_eval,t
G* = final shared DAG across examples, loops, support estimates, and repairs
```

There are two update schedules.

Online schedule:

```text
G'_i = P(G_{i-1}, x_i, y_i, f_i-1)
S_i = MCTS_Select(G'_i, x_i, m_i, H_train)
y_hat_i = Simulate(x_i, S_i)
r_i = H(y_hat_i, y_i, x_i, S_i)
G_i = Accept(G'_i, r_i, replay_i) ? G'_i : G_{i-1}
```

Here sample `i+1` uses `G_i` as the prior graph, but it can still reject, extend,
or split nodes from earlier samples.

Batch schedule:

```text
G'_{i,t} = P(G_t, x_i, y_i, f_i,t-1) for all i
S_i,t = MCTS_Select(G'_{i,t}, x_i, m_i, H_train) for all i
y_hat_i,t = Simulate(x_i, S_i,t) for all i
r_i,t = H(y_hat_i,t, y_i, x_i, S_i,t) for all i
G_{t+1} = BatchAccept(G_t, {G'_{i,t}}_{i=1}^N, {r_i,t}_{i=1}^N,
                      {S_i,t}_{i=1}^N, replay_t)
```

Here every sample in pass `t` proposes from the same accepted graph `G_t`, then
MCTS evaluates that sample's fixed candidate `G'_{i,t}`. The update happens only
after the full pass. This is usually cleaner for experiments because it reduces
order bias.

This gives the training loop:

```text
select -> simulate -> verify -> repair
```

The inference loop is:

```text
select -> simulate/generate -> verify -> accept or repair output
```

So training and inference share the same inner execution process. The difference
is that training updates the skill library, while inference returns the best
candidate artifact or action trace.

This prevents a weak version of the method where the system only labels expert
artifacts with node names. DIRS requires each proposed graph to be tested by
running it.

## Inference Objective

For a new input `(x*, m*)`, DIRS selects a connected sub-DAG:

```text
S* = argmax_{S subset G*} F(S; x*, m*, tau)
```

subject to:

```text
S is connected
S is acyclic
S follows edge directions
every selected content node is supported by x*
forbidden nodes and forbidden edges are excluded
the budget fits the target artifact or action trace
```

A practical objective is:

```text
F(S; x*, m*) =
  sum_{v in S} w_v(x*, m*)
  + sum_{e in S} w_e(x*, m*)
  + R_H(S, x*, m*)
  - P(S, x*, m*)
```

where:

```text
w_v:
  node score from support, evidence fit, role need, domain compatibility,
  budget fit, and rejection penalties

w_e:
  edge score from transition support, dependency validity, no-jump value,
  and forbidden-transition penalties

R_H:
  verifier reward

P:
  penalties for unsupported claims, disconnected nodes, wrong ordering,
  over-budget outputs, or overclaiming
```

The generated output is:

```text
y_hat* = Decode(x*, S*, pi*, b*)
```

where decoding must use the evidence bindings `h*` and follow the selected
topological order `pi*`.

## MCTS Search

MCTS is used because the graph can be rich, but each target needs only one
compatible connected path or subgraph.

A search state is:

```text
s_t = (S_t, pi_t, b_t, h_t)
```

An action can:

```text
add a compatible node
add a valid edge
choose a typed variant
allocate budget
terminate
```

The tree policy can use UCT:

```text
UCT(s, a) = Q(s, a) + c * sqrt(log N(s) / (1 + N(s, a)))
```

After a rollout produces a candidate sub-DAG and draft/action trace, the verifier
returns a reward:

```text
Q(s, a) <- average verifier reward of rollouts using action a from state s
```

The selected path is not the most common path. It is the highest-scoring path
that is connected, evidence-supported, role-compatible, and budget-compatible.

## Blind Generation Constraint

For held-out evaluation:

```text
train on D_train
hide y_test
select S* using only x_test, m_test, G*
generate y_hat_test
then compare y_hat_test with y_test
```

Formally:

```text
y_hat_test = Decode(x_test, S*(x_test, m_test, G*))
```

with:

```text
y_test not in inputs to Select
y_test not in inputs to Decode
```

This is the key difference between learning reusable human skill and copying an
expert artifact.

## Examples Of Human Skills

DIRS can model many expert skills with the same graph machinery.

### Search Question Answering

```text
question intent
  -> query decomposition
  -> source retrieval
  -> source credibility check
  -> cross-source synthesis
  -> uncertainty-bounded answer
```

### Research Gap Proposal

```text
field map
  -> known dominant assumption
  -> missing condition or failure mode
  -> testable gap
  -> feasible method direction
  -> evidence plan
  -> bounded novelty claim
```

### Paper Writing

```text
context
  -> gap
  -> contribution object
  -> mechanism or design
  -> evidence/result
  -> interpretation
  -> scoped takeaway
```

### Code Repair

```text
reproduce failure
  -> localize cause
  -> inspect neighboring pattern
  -> patch minimal code
  -> run focused test
  -> report residual risk
```

### Experiment Design

```text
hypothesis
  -> controlled variable
  -> dataset/task
  -> baseline
  -> metric
  -> ablation
  -> expected interpretation
```

The node content changes by task. The DIRS structure stays the same:

```text
learn latent skill units
learn directed dependencies
learn support and rejection rules
select a connected sub-DAG for the new case
execute or write by following the path
verify and repair
```

## One-Sentence Mathematical Claim

DIRS learns a reusable human skill as a typed directed graph `G*` whose nodes
encode evidence/action units, whose edges encode dependency order, and whose
test-time behavior is the constrained selection and execution of a connected
sub-DAG:

```text
y_hat* = Decode(x*, argmax_{S subset G*} F(S; x*, m*, tau))
```
